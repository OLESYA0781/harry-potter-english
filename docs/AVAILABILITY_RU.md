## 2. Причина: факты отдельно от гипотез

Cloudflare официально описывает ограничения трафика российскими провайдерами, в том числе остановку передачи примерно после первых 16 КБ. Это хорошо согласуется с наблюдением владельца «с VPN работает, без VPN не открывается» и является основной рабочей гипотезой. Это не доказательство конкретной неисправности у провайдера Вики. Ошибку DNS, IPv6-маршрута, TLS или правило Access/WAF ещё нельзя исключить.

Источники:

- [Cloudflare Support: Potential disruption of services for Russian users](https://developers.cloudflare.com/support/troubleshooting/general-troubleshooting/service-disruption/)
- [Cloudflare: Russian Internet users are unable to access the open Internet](https://blog.cloudflare.com/russian-internet-users-are-unable-to-access-the-open-internet)

Из этой среды зафиксировано:

```text
Environment: running, restricted network policy, enforced
DNS through the environment OS resolver:
gaierror: [Errno -3] Temporary failure in name resolution
HTTPS through the configured proxy:
curl: (56) CONNECT tunnel failed, response 403
URLError: <urlopen error Tunnel connection failed: 403 Forbidden>
Proxy response Server: envoy
```

Это ограничение среды Codex, а не измерение из российского интернета и не ответ origin-сервера Cloudflare. TLS-соединение с сайтом не состоялось. Веб-инструмент также не смог открыть production-адрес. Доступа к российскому измерительному узлу и реальному iPhone/Safari нет. Не предпринимались обход прокси, изменение сетевой политики, покупка хостинга или изменение DNS.

Полные безопасные результаты находятся в [availability-observations.json](availability-observations.json). Сборка локально отдала HTML целиком (616 байт), JS (665010), CSS (98224), общую иллюстрацию (504374). Это измерения локальной сборки данного коммита, не замер production. Небольшой HTML сам по себе может загрузиться даже при ограничении больших файлов; поэтому HEAD или единственного HTTP 200 недостаточно.

## 3. Что изменено в репозитории

Учебное приложение, внешний вид, изображения, Auth, SQL/RLS, Supabase URL/key, очередь и разрешение конфликтов не изменялись.

Добавлены:

1. `scripts/check_availability.py` — проверка DNS, TLS/HTTPS, редиректов, полных тел JS/CSS и большой картинки из того же origin. Она сохраняет JSON, не отправляет пароли, токены, ключи, cookies и не читает/записывает результаты ученицы. Соблюдает системный прокси и проверку сертификатов. При наличии прокси отдельная прямая TLS-проба пропускается. Метка сети задаётся пользователем и не является доказательством местонахождения.
2. Браузерная проверка отсутствия внешних CDN/шрифтов и открытия всех уроков без регистрации.
3. Изолированная проверка блокировки только Supabase: приложение продолжает открывать уроки, ответы остаются в локальной очереди после перезагрузки, статус не выдаёт ошибку за успешную синхронизацию.
4. Этот отчёт, план согласования и инструкции проверки.

Никакие настройки нового хостинга не активированы. Ни один новый адрес не опубликован.

## 4. Проверка на реальном интернете Вики

Нужны название домашнего провайдера/мобильного оператора, устройство, браузер и точный текст ошибки. Провести проверку на домашнем Wi-Fi и мобильном интернете при выключенном VPN. Повторить теми же командами с включённым VPN для сравнения. Не очищать данные браузера: в них может быть несинхронизированный прогресс.

Если установлен Python 3, из репозитория:

```sh
python scripts/check_availability.py --label ru-home-no-vpn --output ru-home-no-vpn.json
python scripts/check_availability.py --label ru-home-vpn --output ru-home-vpn.json
```

Сначала выключить VPN перед первой командой, затем включить перед второй. Скрипт не управляет VPN и не определяет географию самостоятельно. Код возврата 0 означает только полную загрузку проверенных файлов, не успешность уроков и облачного сохранения.

Дополнительно на Windows (Командная строка или PowerShell):

```powershell
nslookup -type=A vika-english.pages.dev
nslookup -type=AAAA vika-english.pages.dev
nslookup -type=CNAME vika-english.pages.dev
curl.exe -4 -v -L --connect-timeout 10 --max-time 30 -o site-v4.html https://vika-english.pages.dev/
curl.exe -6 -v -L --connect-timeout 10 --max-time 30 -o site-v6.html https://vika-english.pages.dev/
```

На macOS/Linux использовать `curl` вместо `curl.exe`. В сети с прокси `-4/-6` может выбирать семейство адреса прокси, а не origin; это нужно отдельно отметить. Не удалять AAAA и не менять DNS на основании одной неудачной IPv6-пробы. Для `pages.dev` записями управляет провайдер, не DNS-зона владельца сайта.

В Chrome/Safari Network проверить Document, первый JS, CSS и крупную картинку: статус, полученные байты, длительность, ошибка. Частичная передача около 16 КБ или тайм-аут большого JS при успешном HTML поддерживает гипотезу сетевого ограничения. Полная загрузка JS с последующей ошибкой выполнения — уже другой сценарий, для него нужен текст ошибки Console. HTTP 403 с реальным `CF-Ray`/страницей Access следует сопоставить с Security Events/Access в кабинете Cloudflare; 403 от локального proxy не равен такой ошибке.

В кабинете Cloudflare владелец проверяет проект Vika English, production branch `main`, успешность последней сборки, итоговый домен, привязанные custom domains, Access policies и события WAF/геоблокировки. До просмотра настроек ничего не отключать.

Для Supabase использовать **реальный публичный Project URL** из `VITE_SUPABASE_URL`, без API-ключа:

```sh
python scripts/check_availability.py --supabase-url https://YOUR_PROJECT.supabase.co --label ru-no-vpn --output ru-with-api.json
```

`YOUR_PROJECT` обязательно заменить. Проверка `/auth/v1/health` не запрашивает ответы ученицы. Даже 200 от health не доказывает вход или RPC; 401/403 не означает работающую синхронизацию. Затем вручную проверить вход в существующую учётную запись, восстановление результатов и небольшое обычное учебное изменение на двух устройствах. Не присылать пароли, API-ключи или HAR с токенами.

## 5. Предлагаемое решение на согласование

Если реальные замеры подтвердят отдельную ошибку DNS, редиректа или правила Access/WAF, сначала исправить именно её после просмотра настроек. Если передача обрывается на сетевом маршруте к Cloudflare, изменение уроков не устраняет причину.

**Предлагаемый вариант для проверки — независимый тестовый адрес, без отключения Cloudflare и изменения действующего домена.** Кандидат: Timeweb Cloud App Platform, размещение в России, прямой технический HTTPS-адрес и автодеплой из существующего GitHub. Это предложение, а не уже настроенный или проверенный адрес. Само имя провайдера не гарантирует доступность у каждого оператора — обязательна проверка из сетей Вики.

Официальные инструкции провайдера:

- [Принципы App Platform](https://timeweb.cloud/docs/apps/how-it-works)
- [Подключение репозиториев](https://timeweb.cloud/docs/apps/connecting-repositories)
- [Развёртывание React](https://timeweb.cloud/docs/apps/deploying-frontend-apps/react)
- [Управление сертификатами](https://timeweb.cloud/docs/apps/ssl-certificates)

После согласия владельца:

1. В его аккаунте выбрать тариф/регион и создать отдельное тестовое приложение. Ресурсы могут тарифицироваться; сейчас ничего не создавалось и не покупалось.
2. Подключить только `OLESYA0781/harry-potter-english`, ветку `main`, тип frontend/React. Задать Node 22, установку `npm ci`, сборку `npm run build`, каталог результата `dist`. Настройки Vite должны выдавать готовую статику, не dev server. Если интерфейс провайдера не позволяет задать эти параметры, сначала согласовать конкретную конфигурацию с поддержкой, а не менять код уроков.
3. Скопировать существующие `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` в build-time variables нового приложения. Не создавать новую базу, пользователя или ключ `service_role`. Без этих переменных сайт соберётся, но облачное сохранение будет выключено — такой деплой не принимается.
4. Получить технический адрес и HTTPS-сертификат. Проверить, что маршрут не возвращается на `pages.dev` и не использует Cloudflare как frontend/CDN. Настроить автодеплой обновлений GitHub, сохранив работу через PR.
5. Проверить новый адрес с домашнего и мобильного российского интернета без VPN по разделу 7. Пока проверка не завершена, действующий адрес остаётся основным.
6. После отдельного подтверждения результата выбрать основной адрес. Собственный домен покупать/привязывать и DNS менять только с отдельным разрешением. Если DNS ведётся в Cloudflare, возможен режим DNS-only с адресом **нового origin**, а не CNAME обратно на Pages. Домен поверх прежнего Cloudflare origin не устраняет возможное ограничение IP/CDN.

Доступа к аккаунту Timeweb/регистратору в сессии нет. Настройки и выдачу технического адреса нужно выполнять владельцу по инструкции либо предоставить соответствующий разрешённый доступ после согласования.

## 6. Как сохранить Supabase и несинхронизированные данные

Оставить тот же Supabase-проект, тот же UUID ученицы, RPC `sync_lesson`, RLS и механизм конфликтов. Оба адреса могут синхронизироваться с одной базой. Из-за разных origins локальная очередь и авторизация **не переносятся браузером автоматически**.

До смены основного адреса на каждом старом устройстве:

1. Открыть старый адрес в уже используемом браузере. При необходимости для разовой синхронизации старого адреса временно использовать уже работающий VPN.
2. В панели «Облачное сохранение» скачать резервную копию прогресса. Не очищать localStorage/cookies и не удалять старый сайт из закладок.
3. Дождаться «Синхронизировано» и отсутствия очереди/конфликтов. Конфликт разбирать через существующий выбор версий; не выполнять массовую перезапись.
4. На новом адресе войти в **ту же заранее созданную учётную запись**. Регистрация новой ученицы не нужна. Проверить восстановление старых ответов до внесения новых.
5. Только после этого переключить закладку. Старый адрес сохранить до подтверждения всех устройств; автоматический редирект пока не добавлять.

Если очередь старого устройства не удаётся отправить, перенос этого устройства не завершён. Скачанная JSON-копия — страховка; автоматического импорта такого файла на новом origin сейчас нет. Не вставлять её в localStorage и не импортировать в базу с заменой. Сначала отдельно подготовить проверяемое восстановление с разрешением конфликтов.

Парольный вход сейчас не использует OAuth-редирект; менять Site URL/Redirect URLs в Supabase просто ради тестового адреса не требуется. Если позже настраиваются письма восстановления/OAuth, соответствующие адреса согласовать отдельно.

Если настоящий Supabase тоже недоступен из России, смены frontend-хостинга будет недостаточно. Следующий отдельно согласуемый вариант — небольшой API-шлюз на независимом хостинге к **тому же** Supabase. Он должен пересылать пользовательский Bearer JWT, сохранять RLS, ограничивать upstream и допустимые Auth/RPC-пути, поддерживать обновление сессии, иметь HTTPS, лимиты, тайм-ауты и не логировать токены. Нельзя подменять JWT ключом `service_role` или превращать шлюз в открытый прокси. До проверки реального endpoint этот вариант не реализуется; база и Auth не отключаются. Просто custom domain Supabase меняет имя через CNAME и также не гарантирует смену сетевого маршрута: [Supabase Custom Domains](https://supabase.com/docs/guides/platform/custom-domains).

## 7. Критерии приёмки без VPN

Заполнить на компьютере и реальном iPhone/Safari, в домашней и мобильной российской сети:

- [ ] HTML, весь JS/CSS и все изображения загружаются полностью; нет ошибок DNS/TLS, бесконечного ожидания и циклических редиректов.
- [ ] Открываются Trial Lesson, Lesson 0, Lesson 1, Homework, словарь, нужный Teacher mode и все интерактивные задания без изменения дизайна.
- [ ] Нет новой публичной регистрации; вход существующей ученицы работает.
- [ ] Старые результаты восстановились; новое обычное учебное изменение переживает перезагрузку.
- [ ] Телефон видит изменение компьютера и наоборот после синхронизации.
- [ ] При недоступном API очередь остаётся локальной, а после возвращения сети отправляется через прежний механизм конфликтов.
- [ ] На всех старых origins очереди/конфликты разобраны либо отдельно сохранены для восстановления.

Только после этого можно считать проблему решённой. Успешный тест в облачной среде/зарубежной сети или на localhost не заменяет эти пункты.
