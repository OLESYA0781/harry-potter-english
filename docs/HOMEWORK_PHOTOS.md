# Фотографии Homework 0

В конце `#/homework/0` добавлена кнопка со скрепкой. Можно выбрать несколько
JPG/PNG/WebP до 8 МБ каждый, увидеть превью и открыть оригинал. Фраза
«Проверяет преподаватель.» удалена из интерфейса домашки.

## Один раз включить закрытое облачное хранилище

**Миграция подготовлена и протестирована, но в рабочем Supabase не запускалась:**
в этой среде нет инструмента управления SQL вашего проекта. Владелец одобрил
добавление закрытого Storage. Ответы, пользователи и существующие таблицы
не переносятся, не очищаются и не меняются.

1. Откройте существующий проект Hogwarts English в Supabase.
2. SQL Editor → New query.
3. Скопируйте весь файл
   [`202611030001_homework_photos.sql`](../supabase/migrations/202611030001_homework_photos.sql)
   и нажмите Run **один раз**. Скрипт транзакционный: bucket + две политики.
   Если появится ошибка — сохраните её текст, не удаляйте существующие
   политики/данные ради повтора. Не включайте Public bucket.
4. В Storage проверьте `homework-photos`: Private, 8 МБ, JPG/PNG/WebP.
5. На сайте войдите существующим аккаунтом ученицы, прикрепите одну фотографию.
   Если она выбрана раньше — нажмите «Отправить в облако» у её превью.
6. Дождитесь статуса загрузки файла и синхронизации в панели входа. Откройте
   Homework 0 с тем же аккаунтом на втором устройстве и проверьте оригинал.

Новый тариф, платный ресурс и новые ключи не требуются кодом. Используются
лимиты существующего проекта Storage; автоматическое платное расширение
не подключается. При исчерпании квоты загрузка выдаст ошибку, локальная копия
останется. Проверка реального Storage и iPhone Safari выполняется после SQL.

## Хранение и доступ

- Выбор фото сначала надёжно записывается как Blob в IndexedDB этого origin.
  Это позволяет перезагрузить страницу, продолжить после ошибки Storage или
  отправить фото после входа. Без входа облачная загрузка не выполняется.
- Фото, выбранные вошедшим пользователем, сразу отправляются; после ошибки
  доступна ручная повторная отправка. Гостевые файлы отправляются после входа
  только по нажатию кнопки. Очередь привязывается к user id до загрузки;
  другой аккаунт не видит её и не наследует.
- Закрытый bucket `homework-photos`, путь `user-id/homework-0/uuid.ext`.
  Storage RLS требует свой user-id и существующее членство lesson_students.
  Анонимным и другим пользователям доступ закрыт. Обновление файлов запрещено;
  для удаления владельцем используется отдельная политика, описанная ниже.
- В progress сохраняются только небольшие метаданные под независимыми ключами
  `@vika/lesson/lesson-0-homework/photo/uuid`, без base64/Blob и без signed URL.
  Используется прежний journal/outbox/CAS. Запись метаданных происходит после
  загрузки файла и подтверждения доступа к нему. Ответы не меняются.
- Ссылки на облачное превью подписываются на 10 минут, без публичного bucket.
  Локальный оригинал сохраняется и после загрузки; очистка браузера или смена
  домена удаляет доступ к локальной очереди, но не загруженный объект в облаке.
  JSON-backup прогресса не включает бинарные файлы: не очищать браузер, пока
  фото не появилось на втором устройстве.
- HEIC/SVG/PDF не принимаются. На iPhone выбрать совместимый JPG/PNG либо
  экспортировать HEIC в JPG. Файлы проверяются на размер, тип и возможность
  декодирования до записи. Сервер ограничивает размер и MIME через bucket.

## Проверки

`npm run build`, unit-тесты; `node tests/sql/photos.mjs` проверяет миграцию
на PGlite со схемой Storage (private, членство, изоляция пользователей,
запрет анонимного доступа/изменения/удаления). Это не эмуляция самого Storage
сервера: реальное применение MIME/size limit требует приёмки на Supabase.

Браузерные сценарии: два фото и ответы переживают reload, недопустимые типы
отклоняются, размеры 390/820/1440 без overflow. Cloud mock: отсутствующий bucket,
локальная очередь, повтор, private upload + signed preview, метаданные на
другом устройстве. Настоящий Safari/российская сеть пока не проверены.

## Удаление фотографий

У каждого фото — кнопка с корзинкой «Удалить фото» и подтверждение. Локальные
гостевые фото удаляются из IndexedDB. Облачные удаляются через Storage API,
после чего общий progress получает маркер `{deleted:true,id,owner}` под тем же
ключом фото. После синхронизации другие устройства скрывают фото и удаляют
свою локальную копию. Текстовые ответы и остальные фотографии не затрагиваются.
Маркер является объектом: обычный null журнал убирает из state при expand,
что не позволяет отличить удаление от ещё не отправленного локального файла.

Для удаления облачных файлов нужно **один раз** выполнить дополнительный
SQL в существующем Supabase → SQL Editor → New query → Run:
[`202611030002_homework_photos_delete.sql`](../supabase/migrations/202611030002_homework_photos_delete.sql).
Этот скрипт подготовлен/протестирован, но не выполнен в рабочем проекте из
этой среды. Он добавляет только DELETE policy для собственного homework-0
каталога авторизованного участника lesson_students. Public-доступ не включается,
прежние политики/таблицы не меняются, никакие файлы самой миграцией не удаляются.

Намерение удаления записывается в IndexedDB до Storage-запроса. При обрыве сети,
недостающей политике или reload доступна кнопка «Повторить удаление». Фото не
объявляется удалённым только по успешному HTTP DELETE: Storage может вернуть
пустой список при запрете RLS. Проверяется именно отсутствие объекта через
sign endpoint. При непонятном ответе операция остаётся незавершённой. Перезапуск
не приводит к повторной загрузке такого файла. После удаления старые уже
скачанные копии на чужих устройствах/вне приложения отозвать невозможно.

Проверки удаления: cancel/confirm/reload и сохранность ответов на трёх размерах;
Storage mock с отсутствующим DELETE policy, повтор после reload, удаление на
втором устройстве и очистка Blob первого; SQL-изоляция для anonymous/другого
пользователя/неучастника и разрешение только владельцу.
