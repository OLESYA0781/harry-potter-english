# Синхронизация ответов и прогресса в Supabase

Сайт использует существующую учётную запись Вики и сохраняет ответы локально, в том числе без подключения к Supabase. Для преподавателя можно связать отдельную учётную запись с существующей записью Вики.

## 1. Supabase и единственная учётная запись

1. Создайте Supabase project. В Authentication → Sign In / Providers оставьте вход Email + Password. Отключите **Allow new users to sign up** (публичную регистрацию), anonymous sign-ins и ненужные провайдеры. В интерфейсе приложения регистрации нет.
2. В Authentication → Users → Add user → Create new user создайте одну ученицу с email и сильным паролем. Подтвердите email через Auto Confirm или штатное подтверждение. Передайте пароль ученице по защищённому каналу. Не помещайте его в Git, Cloudflare Pages env или чат.
3. В SQL Editor выполните `supabase/migrations/202610260001_lesson_sync.sql` **один раз**. Альтернатива для проекта с Supabase CLI — обычный процесс `supabase db push` после привязки проекта. Миграция создаёт две таблицы, RLS и RPC; она не создаёт пользователя и не включает его автоматически.
4. Скопируйте UUID созданного пользователя из Authentication → Users и выполните в SQL Editor, заменив UUID:

```sql
insert into public.lesson_students(user_id)
values ('REPLACE_WITH_CREATED_USER_UUID'::uuid)
on conflict do nothing;
```

Оставьте в списке учениц существующий UUID Вики. Проверить список можно следующим запросом.

```sql
select user_id from public.lesson_students;
```

5. В Authentication → URL Configuration укажите Site URL вашего HTTPS-сайта Cloudflare Pages. Redirect URLs добавляйте только для доверенных адресов, если будете использовать подтверждение email или восстановление пароля. Приложение использует парольный вход без redirect и не предоставляет самостоятельный password-reset flow. Восстановление учётной записи выполняет владелец проекта через Supabase.

## 2. Обновление существующего проекта

1. В SQL Editor проверьте, что UUID Вики из Authentication → Users присутствует в `public.lesson_students`. Вика использует этот же аккаунт на телефоне и компьютере.
2. Примените `supabase/migrations/202611260001_answer_sync.sql` через SQL Editor или связанный Supabase CLI. Миграция сохраняет точную копию старых записей в закрытой таблице `public.lesson_progress_legacy`. Существующие пользователи, рабочие таблицы, маркеры импорта и настройки аудио остаются доступны.
3. Для отдельного входа преподавателя используйте её существующий аккаунт Supabase Auth. Если такого аккаунта ещё нет, владелец проекта может создать его в Authentication → Users. Свяжите два UUID в SQL Editor.

```sql
insert into public.lesson_teachers(user_id, learner_id)
values ('TEACHER_AUTH_UUID'::uuid, 'VIKA_AUTH_UUID'::uuid);
```

4. Опубликуйте новую сборку сразу после миграции. Старый RPC перестаёт принимать запросы при применении миграции. До обновления страницы старые вкладки продолжат сохранять изменения в локальной очереди. Перезагрузите их с подключением к сети и войдите под тем же аккаунтом.
5. Проверьте на рабочем проекте вход Вики на двух устройствах и вход преподавателя под своим UUID. После входа преподаватель открывает нужный урок и включает Teacher mode. Проверьте изменение, очистку и восстановление офлайн-очереди. В режиме Realtime таблица `lesson_progress` включается в публикацию `supabase_realtime`, если публикация существует. Проверка каждые пять секунд работает и при отключённой публикации.

## 3. Переменные Cloudflare Pages

Переменные находятся в настройках проекта Cloudflare Pages → Variables and Secrets для production (и отдельно для доверенных preview-сборок при необходимости). Существующие значения рабочего проекта сохраняйте:

| Переменная | Значение |
| --- | --- |
| `VITE_SUPABASE_URL` | `https://YOUR_PROJECT.supabase.co` из Project URL |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | публичный `sb_publishable_…` из API Keys; допустим старый anon key |

Это переменные **этапа сборки** Vite, они видны в браузере. Не используйте secret key, `service_role`, пароль ученицы, JWT secret или строку подключения к БД. Доступ защищают Auth + серверный allowlist + RLS, а не сокрытие публичного ключа.

Проект публикуется через Cloudflare Pages: корень репозитория, Node 22, команда `npm run build`, результат `dist`, production branch `main`. После изменения переменных нужна новая сборка Pages. Новые уроки используют существующий Auth, локальную очередь и версионирование ответов. Подробности о добавлении уроков есть в `LESSONS.md`.

Локально: скопируйте `.env.example` в `.env.local`, заполните два публичных значения, затем `npm ci` и `npm run dev`. `.env.local` исключён из Git. Для синхронизации используйте HTTPS или localhost; Web Locks координируют вкладки в современных браузерах. При отсутствии Web Locks остаётся последовательная очередь одной вкладки; для одновременной работы вкладок используйте актуальные Chrome/Safari/Firefox.

## 4. Первый перенос и смена устройства

1. На **прежнем устройстве**, в том же браузере и на том же домене, где ученица занималась, обновите сайт. Смена домена или профиля браузера не переносит localStorage.
2. Откройте «Облачное сохранение», войдите созданной учётной записью и дождитесь окончания синхронизации.
3. До первого запроса с данными урока создаётся неизменяемый снимок исходного локального прогресса. Он остаётся в поле `backup` журнала `hogwarts-cloud-v1` и входит в кнопку «Скачать резервную копию прогресса». Облачные изменения не заменяют этот снимок.
4. Импорт версий localStorage 1, 2, 3 выполняется после входа, с сохранением прежних правил переноса номеров глав. Серверный маркер делает повтор запроса безопасным. Импорт добавляет только **отсутствующие поля**: локальные старые данные без временных меток никогда не перезаписывают существующие облачные значения, включая удалённые ответы. В уроках, перенесённых из старой базы, отсутствие поля также может означать очистку. Такие поля остаются в облачной записи пустыми. При пропусках показано уведомление, исходные данные доступны в резервной копии.
5. На другом устройстве войдите тем же аккаунтом. Данные подтянутся автоматически. Страницы обновляются при открытии, возврате на вкладку, восстановлении сети и уведомлении Realtime. Резервный опрос выполняется каждые 5 секунд. Запись запускается через 600 мс после изменений. Кнопка синхронизации позволяет запросить проверку сразу.

`hogwarts-english-v1` сохраняется как совместимая копия состояния. `hogwarts-cloud-v1` хранит владельца, облачные версии, очередь изменений, маркер импорта и резервную копию. Перед асинхронной обработкой каждый ввод синхронно записывается в `hogwarts-outbox:*`: даже немедленная перезагрузка до освобождения блокировки вкладки не теряет изменение. Запись очереди подтверждается прежде, чем отправляется в облако. Успешно принятые операции удаляются; ошибки сети и потеря ответа не очищают очередь. Не очищайте данные браузера до синхронизации/экспорта.

Ответы имеют отдельные ключи по уроку и заданию. У Lesson 1 отдельная версия у каждого черновика Present Simple, а посещённые темы записываются по одной. В Homework 3 каждая ячейка таблицы, выбор и отметка в тетради синхронизируются отдельно. Порядок слов и игровые доски, где несколько элементов образуют один ответ, сохраняются как единое задание. Homework 2 выполняется в тетради и содержит ключ преподавателя.

## 5. Конфликты, отсутствие сети, Restart

RPC `sync_lesson_answers` блокирует строку ученицы на время изменения, сравнивает базовую версию каждого поля с текущей и назначает принятому изменению следующую версию и время PostgreSQL. Исторические поля получают время прежнего документа, поскольку отдельные отметки времени раньше отсутствовали. Часы браузеров не определяют порядок принятия записей.

Правки разных ответов объединяются. При конфликте одного ответа отображается подтверждённая серверная версия, а локальный вариант сохраняется в экспортируемой резервной копии. Для старых составных полей используется слияние независимых частей, когда это сохраняет корректность задания. Очистка сохраняется с собственной версией. Идентификатор мутации делает повтор после потери ответа безопасным.

`Saving...` отображается при сохранении, `Syncing...` при подключении или восстановлении, `Offline` при отсутствии подключения, `Sync error` при ошибке. `Saved` появляется после подтверждения сервера. Очередь переотправляется автоматически.

**Restart lesson — намеренный сброс**: он синхронизирует пустые значения и tombstones ответов, результатов и оценок, поэтому старый импорт не восстанавливает удалённое. Исходный снимок первого переноса остаётся в резервной копии.

После потери сети уже открытый урок продолжает работать и сохранять изменения. Это не offline PWA: первая загрузка/перезагрузка сайта без сети не гарантируется. Первый вход и обновление истёкшей сессии требуют интернета. SDK Supabase сохраняет и обновляет сессию; выход не удаляет очередь или прогресс. Браузер связан с UUID первой ученицы и откажется переносить эту очередь в другой аккаунт.

## 6. Безопасность и проверки

Таблицы защищены RLS. `anon` не может читать или писать. Вика видит запись своего UUID, преподаватель получает доступ только к назначенной записи. Учебные поля доступны преподавателю для существующих действий Teacher mode. Прямые INSERT, UPDATE и DELETE запрещены. RPC проверяет `auth.uid()`, определяет ученицу по серверному списку и сверяет её с ожидаемым UUID журнала. Старый снимок БД и таблица назначений доступны администратору. Права закрытого хранилища фотографий регулируются отдельными политиками Storage.

```sh
npm ci
npm run build
npm test
npm run test:sql
npm run test:e2e
npm run test:cloud
```

`test:sql` выполняет настоящую миграцию и проверки доступа на изолированном PostgreSQL PGlite, с минимальными заглушками схемы Auth и ролей. `test:cloud` запускает Chromium, официальный Auth SDK и ту же SQL-функцию на PGlite; сетевые Auth/PostgREST endpoints заменены тестовым сервером маршрутов. Производственные ключи и база не используются. `test:e2e` проверяет уроки и экранные результаты без конфигурации Supabase. Для Chromium задайте `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`, если он расположен не в `/usr/bin/chromium`.

Браузерные тесты используют независимые контексты Chromium и тестовые точки Auth, PostgREST и Realtime. На рабочем проекте проверку следует повторить после миграции и публикации.

При откате к прежней версии сайта сохраните JSON-резервную копию и не удаляйте облачные таблицы. Старый сайт не знает об облаке; при возвращении новой версии журнал имеет приоритет над совместимой localStorage-копией. Не редактируйте вручную ключи очереди. JSON-экспорт предназначен для сохранности/ручного восстановления владельцем проекта; автоматической загрузки произвольного JSON нет.
